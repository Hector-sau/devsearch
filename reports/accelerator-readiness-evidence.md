## 0. Read this first / 先读这里

**This is engineering evidence on CPU in one Linux container. Most of it uses synthetic and diagnostic data; the rest uses one real public corpus with questions that an agent workflow wrote and an independent agent reviewed. It is not accelerator readiness and not a reranker result.** There is no MPS or CUDA run, no pinned real MiniLM or tokenizer (the real-corpus steps use an unpinned BERT-uncased vocabulary stand-in, so everything derived from it is conditional), no human review and no judged candidate-review bank. The phrase "only the GPU is left" is **false**: the open items in section 4 include assets, human review of the labels, the candidate judgments, target-machine lock installation and CI, none of which a GPU provides. Estimates (section 3) are kept apart from measurements. The only ranking numbers quoted are the BM25-only figures on 202 synthetic validation questions (2.8); they say nothing about a reranker or about real user queries. Every ranking metric inside `rehearsal/` comes from a planted synthetic cue and is not quoted.

**这是在单个 Linux 容器 CPU 上的工程证据。大部分使用合成与诊断数据；其余使用一个真实公开语料，问题由 Agent 工作流撰写、并由独立 Agent 审查。它不是加速器就绪，也不是重排结果。**尚无 MPS／CUDA 运行、固定的真实 MiniLM 与分词器（真实语料步骤使用未固定的 BERT-uncased 词表替代，因此其衍生结果都是有条件的）、真人审查或已判定的候选审查库。“只差 GPU”的说法**不成立**：第 4 节的未决项还包括资产、标注的真人复核、候选判定、目标机依赖锁安装和 CI，GPU 都不能提供。估算（第 3 节）与实测分开。唯一引用的排序数字是 202 个合成验证问题上仅 BM25 的结果（2.8），它们不说明重排，也不代表真实用户问题；`rehearsal/` 内的排序指标来自合成的植入线索，此处不引用。

**A defect that real data exposed.** Reading one real search result showed a document titled "Conclusion" whose text began with its real title. The RST reader required an underline at least as long as the title, but docutils accepts a shorter one (four or more characters). Nine document titles were wrong ("Prerequisites", "Overview", "Conclusion" and similar) and 254 of 4,255 chunk ids changed once fixed (commit `33674e7`, regression test `test_an_underline_shorter_than_its_title_is_still_a_heading_but_a_tiny_adornment_is_not`, parser version declared `static-extract-v2`). A title audit of the rebuilt corpus found no generic titles left.

**What this says about the data protocol.** After the rebuild, the audited assignment moved 489 of the 1,178 previously selected passages to another split, so a labelled question set belongs to one corpus build and must be regenerated or carried over by exact chunk id and text (`carry_generations.py` does the latter) whenever the reader or the tokenizer changes.

**What the baseline numbers mean, and do not.** BM25 already scores near the ceiling on these questions, so this set leaves a reranker little to gain: an agent writing a question while reading a passage reuses that passage's vocabulary, which favours lexical retrieval. The figures describe BM25 on agent-written validation questions with one judged positive each (other relevant passages count as misses). They are not a result for real user questions, say nothing about a reranker (none was trained or run), and are not a latency for the reranked pipeline.

**Generation notes.** The question and review agents are sub-agents of this session. A usage limit was reached once while 20 review agents ran; the affected batches were run again, and every review file was then checked for matching refs, valid verdict fields and answer length (two answers in one file exceed 25 words; their verdicts are unaffected). Measured roughly from the agents' usage reports: generating 1,190 questions and reviewing 1,000 took about 60 agent runs of 60,000–90,000 tokens each.

## 3. Estimates kept apart from measurements / 估算与实测分开

**Measured here (CPU only):** the wall times in 2.1–2.8; storage: real snapshot 184 MB, prepared real data (`prepared2`, 4,259 passages, indexes, pairs, candidates) 22 MB, diagnostic rehearsal tree 8.5 MB, backup 1.3 MB, `apple-mps` wheelhouse 191 MB, `nvidia-cuda` wheelhouse 3.0 GB, CUDA-lock environment 6.0 GB; BM25-only latency on the real index (2.8: p50 0.857 ms, p95 2.00 ms, a proxy workload).

**Estimates (labelled `estimate` in the plan):** the diagnostic plan estimated 6.0 s of work for stages it can estimate (`train:frozen` 0.30 s vs 0.36 s observed, `train:full` 0.86 s vs 0.68 s, `latency` 3.0 s vs 0.35 s, `rank_test` 0.60 s vs 0.09 s; stages without a measured rate carry `estimate: null`). This only shows the estimator's mechanics on a tiny CPU model. **No accelerator time, no real-model time, no human review time and no judging time was measured**; the figures in docs/12 remain illustrative assumptions. The only cost measured for real-data labelling is the agent effort in 2.8 (about 60 sub-agent runs for 1,190 questions plus 1,000 reviews); an agent pass over the 9,852-item review pool at 40 items per run would be about 250 runs, which is an **extrapolation, not a measurement**, and it would still be agent judgment, not human review.

## 4. Open blockers and next action / 未决阻塞项与下一步

**The project is not GPU-ready and is not labelled so.** The gates that apply to a formal run are: `implementation_verified` passed (on CPU, snapshot `225ea98d…`), `portable_bundle_verified` passed for the diagnostic rehearsal only, `data_ready` **unverified**, `backend_verified[apple-mps]` and `backend_verified[nvidia-cuda]` **unverified**. `accelerator_run_ready` is false.
